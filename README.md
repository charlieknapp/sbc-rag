# sbc-rag
RAG-based Q&amp;A tool for health benefit plans — parses real SBC (Summary of Benefits and Coverage) forms, retrieves and extracts plan data, and answers questions like "what's my deductible for an ER visit" with cited sources. Built to explore retrieval, structured extraction, and grounded generation on table-heavy insurance documents.

## Project Structure

```
sbc-rag/
├── app.py                    # Streamlit UI
├── requirements.txt
├── data/
│   ├── raw/                  # original SBC PDFs, untouched
│   └── processed/            # per-plan parsed JSON, chunks.json, plan_facts.json
├── src/
│   ├── parsing/               # PDF -> structured text/tables
│   ├── chunking/               # row-level chunking
│   ├── retrieval/               # BM25 + embeddings

│   └── generation/               # evidence gathering, comparison, service coverage,
│                                 # direct lookup, LLM synthesis, pipeline entry point
├── notebooks/                # ad-hoc validation scripts, one per phase/fix
└── eval/
    ├── questions.jsonl       # 27-question eval set + expected answers
    └── run_retrieval_eval.py # retrieval-only hit-rate eval
```

### Running the app

```
streamlit run app.py
```



Launches a local web UI for asking questions against the pipeline interactively — type a question and get back the answer with a confidence badge, its citations (each labeled `verified data` or `SBC text`), any citation-verification issues, and the per-question latency/token/cost. An expander below the main question box also lets you run the full 27-question eval set from the browser — it takes about 90 seconds and $0.22 in API usage, and returns a results table plus aggregate totals.

## How It Works

### 1. Parsing
Every SBC is federally templated, but that consistency turned out to hold at the section level, not the extraction level — no two documents rendered their tables the same way underneath, and several looked visually identical while breaking differently on inspection.

**Grid table and Important Questions table.** Both use `pdfplumber`'s table extraction (tuned tolerances — `snap_tolerance`/`join_tolerance`/`intersection_tolerance`/`edge_min_length` all set to `5`, found through a controlled default-vs-tuned comparison after a wrong first guess of `8` caused real cross-row text bleed) as the default path, with `camelot` (lattice mode, reading actual ruling lines instead of clustering text positions) substituted in for four documents whose specific defects pdfplumber couldn't handle: UnitedHealthcare (a duplicate invisible text layer — a legitimate PDF accessibility feature that confused every text-based extractor equally, fixed by stripping render-mode-3 text directly from the content stream), Cigna (decorative shading rectangles that pdfplumber's line-detection mistook for real row boundaries), Blue Shield CA and Anthem (a stray footnote and a mid-page table split, respectively, that camelot's ruling-line-based extraction simply didn't trip over). Which library and which table spec each document needs is captured once in `src/parsing/document_registry.py`, not re-decided per script.

Raw table output — from either library — still isn't usable directly: merged cells, blank continuation rows, and wrapped multi-line labels all needed a shared normalization pass (`src/parsing/normalize.py`) that forward-fills blank category labels, merges orphaned overflow text onto the correct row, and tracks state across page breaks. The same normalization logic, generalized around a `TableSpec` dataclass, handles both the "Common Medical Events" grid table and the "Important Questions" table (different column shapes and merge semantics, same underlying blank-continuation pattern).

**Non-table content.** Header metadata (insurer, plan name, coverage period, plan type) and the Excluded Services / Other Covered Services bulleted lists are extracted separately, since neither is a ruled table. Header metadata is pulled line-by-line with marker-based field detection, falling back to the document registry (not PDF text) for insurer name on the several documents where it's rendered as a logo image rather than text. Excluded/Other Covered Services required a different technique entirely — both lists are laid out as multi-column bullet grids with no ruling lines and, on at least one document, no enclosing rectangle at all — so they're reconstructed directly from word-level `(x0, top)` positions: bullet characters anchor column positions, rows are split into segments by horizontal gap, and each segment is assigned to its nearest column by its own leading position.

**Out of scope, by design:** the three standardized coverage examples every SBC prints (having a baby / managing diabetes / simple fracture) were never extracted as their own artifact. Each one is a worked illustration built from figures already captured elsewhere — the deductible, copay, and coinsurance amounts behind them are the same numbers already pulled from the grid table rows — so extracting the examples separately would mean parsing a second representation of information the pipeline already has, not adding anything new. Language-access boilerplate and legal disclaimers are excluded for the same reason — no answerable content lives there.

**Validation.** All 8 documents were checked by hand against their actual rendered PDFs (not just row/item counts), and a full 8-document regression pass was run against the final codebase after every document was individually validated — this caught one real bug (a fix made for one document silently dropping a valid row on another) before it could ship. A few small, low-severity artifacts remain and are documented in code rather than fixed: isolated single-character word splits on 2-3 documents, and one cosmetic field-boundary issue on Anthem's header (a value that lands split across two fields instead of one, nothing lost).

**Output.** Validated extraction results are persisted to `data/processed/` as one JSON file per document (`notebooks/build_processed_data.py`), rather than re-running PDF extraction on every downstream iteration — chunking and every phase after it reads from this stable artifact, which also keeps a parsing bug and a downstream bug from being confused with each other.

### 2. Chunking

Because the source PDFs are already reduced to clean, structured JSON in `data/processed/` before chunking runs (see Parsing above), the fixed-size vs. semantic comparison this project calls for could be tested directly against real data rather than argued from first principles.

**Fixed-size chunking was tested and measurably fails the "never split a row mid-chunk" requirement.** A naive character-window chunker (with overlap) was run against the flattened text of two documents at three window sizes (300/500/800 characters), tracking each row's exact character span so violations could be counted rather than eyeballed. Result: 28-62% of rows were split mid-chunk depending on window size, and the violation rate never approached zero even at the largest size tested — row lengths vary enormously (a ~110-character row sits next to a ~1,500-character prescription drug row), and a fixed-size window has no way to know where a row's boundary actually is. No window size is simultaneously small enough to keep chunks focused and large enough to never cut a row on this data.

**Semantic (embedding-based) chunking was tested and found to be a real but imperfect signal.** Using local embeddings (`sentence-transformers`, `all-MiniLM-L6-v2` — the same model reused for the retrieval phase) consecutive-row cosine similarity was computed across all 8 documents and compared against the grid table's own real category boundaries — already known with certainty, since they're extracted directly during parsing — using precision/recall/F1 across a threshold sweep. The best single threshold (0.65) recovered the true category structure with F1 = 0.840 (precision 0.863, recall 0.833): a real, well-above-random signal, but not perfect, and no threshold cleanly separates every case (two rows in the *same* category scored a lower similarity, 0.627, than two rows in genuinely *different* categories at 0.786).

**Decision: structured, row-level chunking — not fixed-size or similarity-threshold chunking.** Since the real category/row boundaries are already known with zero error from parsing, using a noisy ~84%-accurate embedding proxy to rediscover them would be strictly worse than simply using the boundary already extracted. Chunks are built directly from `data/processed/*.json`'s row structure (`src/chunking/chunker.py`): one chunk per grid table row and one per Important Questions row, with category, service/question text, and plan identity folded explicitly into each chunk's text (a retriever hands back isolated chunks with no surrounding context, so each one has to be self-describing); one chunk per whole Excluded Services / Other Covered Services list (list items showed no meaningful internal similarity signal worth grouping by); and one small chunk per document for header-level facts (deductible, plan type, coverage period). This satisfies "never split a row mid-chunk" exactly, by construction — a chunk *is* a row — rather than by tuning a threshold and hoping.

320 chunks were produced across all 8 documents (`data/processed/chunks.json`), with per-document counts cross-checked against the already-validated parsing row/item counts for every document.

### 3. Retrieval

With 320 chunks in hand, retrieval's job is narrowing that down to a handful of chunks actually relevant to a given question — the project looks at both a keyword method and a semantic method, tested against real questions rather than assumed to behave a certain way.

**BM25 (keyword search)** (`src/retrieval/bm25_retriever.py`, via `rank-bm25`) scores chunks by word overlap with the query, weighted by term rarity and adjusted for chunk length — no understanding of meaning, purely lexical matching. Custom tokenization strips punctuation and a hand-curated stopword list; a real bug was caught and fixed here via a failing test query, not assumed away — the initial tokenizer left bare single-character fragments like `'s'` (from splitting contractions such as "What's") untouched, which measurably diluted real signal on short queries. Fixing it (filtering tokens of length 1) took BM25 on one previously-failing test question from 0/8 relevant chunks found to 6/8.

**Semantic search (embeddings)** (`src/retrieval/embedding_retriever.py`, via `sentence-transformers`'s `all-MiniLM-L6-v2` — the same model used for the chunking-boundary evaluation — and FAISS's `IndexFlatIP` over L2-normalized vectors, i.e. exact cosine similarity) embeds both the query and every chunk, retrieving by vector closeness rather than literal word match. FAISS was chosen over the more common Chroma because this is a plain vector-similarity lookup with no need for Chroma's extra features (persistence, metadata filtering) — the 320 chunks are rebuilt fresh from chunks.json on every run.

**Evaluation.** A 27-question eval set (`eval/questions.jsonl`) was built directly from the real chunk data, with ground-truth `chunk_id`s and expected answers — not approximated from summary values — spanning five deliberate categories: exact-SBC-vocabulary lookups, paraphrased questions, questions using rare/distinctive terms, questions naming no specific plan (genuinely ambiguous across all 8), cross-plan comparison questions, and one deliberately unanswerable question (a plan that doesn't exist in the corpus, to probe fabrication risk). `eval/run_retrieval_eval.py` runs both retrievers at k=5 (matching the top-k that will actually reach the LLM at generation time) and reports hit-rate by category:

| Category | BM25 | Embeddings |
|---|---|---|
| Exact vocabulary | 100% | 100% |
| Paraphrased | 50% | 67% |
| Rare/distinctive terms | 100% | 75% |
| No plan named (ambiguous) | 80% | 80% |
| Cross-plan comparison | 60% | 60% |

**This is the core, measured result the phase was built to test:** BM25 and embeddings do win on different, predictable question types — BM25 on distinctive vocabulary, embeddings on paraphrased wording — confirming the hypothesis with real numbers instead of assuming it. Both tie on easy exact-match lookups, as expected.

**Real failure modes found and root-caused, not just observed:**
- *Confusable adjacent rows*: a query like "what do I pay to see a specialist" can outrank the true cost row with a topically-adjacent "do you need a referral to see a specialist" row, since both share real vocabulary/meaning around paying for specialist care despite answering different questions. Embeddings are less confidently wrong here (near-tied scores) than BM25 (a 3x score gap favoring the wrong row), but neither method is immune.
- *Uniform boilerplate crowding*: on plans with unusually flat cost structures (e.g. Cigna's plan, where deductible = out-of-pocket max, so nearly every service reads "0% coinsurance"), embeddings can fail to distinguish between many near-identical chunks and miss the specific one asked about entirely.
- *Genuine SBC-vocabulary gaps*: some real-world phrasing (e.g. "therapy visit") has no literal match anywhere in the source document's own text (which says "outpatient services," never "therapy") — a gap in the source data's vocabulary, not a retrieval bug, that keyword matching structurally cannot bridge and embeddings can only partially close.
- *Term-frequency bias toward complex answers*: BM25 can underrank the simplest, most favorable answers (e.g. a $0 deductible, explained in one short sentence) relative to more complex ones that repeat the query term more often purely because they require more explanatory text — a structural property of frequency-based scoring, not a bug.

Note: the eval table above reflects k=5, the value used during Retrieval's own isolated evaluation. In later end-to-end testing (see Evaluation), two questions' correct chunks were found ranking just outside that top-5 window (ranks 6 and 9) — k was subsequently widened to 10 for actual generation use, trading a modest cost/latency increase for those recovered cases. The retrieval-only comparison above is left at k=5 since that's what isolates BM25 vs. embeddings behavior cleanly; k=10 is a downstream generation-pipeline decision, not a change to this phase's own findings.

### 4. Structured Extraction

Retrieval hands back relevant chunks, but the raw chunk text still requires an LLM to read and interpret every time a question is answered — for a handful of headline numbers every plan publishes (deductible, out-of-pocket max, referral requirement), that's unnecessary risk in a project whose whole goal is no hallucinated numbers. This phase pulls those specific facts out once, offline, into a typed, pre-validated artifact (`data/processed/plan_facts.json`) that generation can optionally cite against directly — a distinct, batch step, not a per-question runtime process, the same way chunking is.

**Schema** (`src/extraction/schema.py`, Pydantic `BaseModel`) is a deliberate departure from the plain dataclasses used everywhere else in this project (`Chunk`, `RetrievalResult`) — chosen specifically for runtime validation, catching a malformed extracted value at construction time rather than relying on static type hints alone. `PlanFacts` holds `deductibles`/`out_of_pocket_maxes` as `list[AmountEntry]` rather than fixed named fields (`individual_deductible`, `family_deductible`, ...), because the real data has more independent splitting dimensions than any fixed field set could cover cleanly: individual/family, in-network/out-of-network, Anthem's 3-way person/member/family split, Blue Shield CA's and Kaiser's secondary medical/pharmacy category axis, and per-field asymmetry (UHC's deductible has no network split; its OOP max does). `AmountEntry` supports a real `Unlimited` value (several plans' out-of-network OOP max is genuinely uncapped) via an `is_unlimited` flag that a custom validator enforces is mutually exclusive with a numeric `amount`. A `referral_required: bool | None` field is paired with `raw_referral_text: str`, added after finding a real case (Kaiser: *"Yes, but you may self-refer to certain specialists"*) that a plain bool can't represent — the bool stays a clean signal for generation to key off, the raw text preserves the nuance rather than silently dropping it. Scope deliberately kept narrow to deductible / OOP max / referral only — service-level copay/coinsurance stays retrieval-only text, not pulled into the schema.

**Extraction technique: rule-based/regex, not LLM-based** — a deliberate choice to keep this trusted-ground-truth layer free of the exact hallucination risk the project is trying to eliminate elsewhere. The core design principle: fail loud and return unextracted on unrecognized input rather than guess — a wrong-but-confident extraction is more dangerous here than an honest gap.

Before writing any parsing code, all 16 real answer strings (8 plans × 2 fields) were pulled and compared, which cut the expected shape count from a feared 16 (one per insurer × field) down to ~9-10 — several insurers' shapes turned out to be directly reusable across both fields, and the generalized shape count only grows per distinct *(insurer, field)* structure, not per insurer. Ten distinct parser functions were built and independently validated against real per-plan text, covering patterns from simple single values to multi-tier splits to insurer-specific quirks (e.g. Highmark's de-duplication, Kaiser's OOP format).

**Real PDF-extraction artifacts caught via actual test output, not assumed away** — the same recurring "stray character" family documented back earlier kept resurfacing at every layer of this phase: Anthem's `"Non- Network"` (stray space after a hyphen) silently dropped 3 of 6 expected out-of-network entries the first time through; UHC's real question text uses an en dash (`"out–of–pocket"`) where every other insurer uses a hyphen; Anthem's and Cigna's OOP question text has a stray space (`"out-of- pocket"`); and Highmark's referral question has a literal typo (`"referral t see"`). All handled by a shared `clean_text()` normalization step rather than one-off insurer-specific patches, applied before matching/parsing — deliberately scoped narrowly (e.g. only collapsing a post-hyphen space before a lowercase letter) so it doesn't interfere with cases that already have their own tested whitespace tolerance downstream. Also found and fixed: chunk-lookup markers that were initially too loose and silently matched the *wrong* question on the same SBC (e.g. "deductible?" matching both "what is the overall deductible?" and "are there other deductibles for specific services?"), and inconsistent trailing punctuation before "Why this matters:" (single period on 3 plans, double on the other 5) that caused a too-strict regex to silently return nothing.

**Driver** (`src/extraction/driver.py`) ties chunk lookup and parsing together via an `EXTRACTOR_REGISTRY` dispatch table — a `document_registry`-style mapping, this time keyed by `(source_filename, field)` rather than insurer name, since `source_filename` is the one unambiguous identifier already used throughout. `raw_deductible_text`/`raw_oop_max_text`/`raw_referral_text` deliberately store the true original, pre-cleanup answer text (not the artifact-normalized version fed to the parsers) — "raw" means raw, both so it's genuinely citable against the real source and so a future bug in `clean_text()` would show up as a visible diff rather than disappearing into a field labeled raw.

**Validation.** `data/processed/plan_facts.json` (all 8 plans) was checked two ways: a full line-by-line review against the real source text independently confirmed throughout this phase's development, and a direct comparison against this README's own SBC Sources table (Earlier hand-verified ground truth, sourced from the actual published SBC PDFs, built before any extraction code existed). **All 8 plans matched exactly on both fields — 100% agreement, no discrepancies.** One apparent mismatch on inspection turned out not to be one: Anthem's ground-truth table shows 2 OOP numbers while the extracted output has 3 entries (person/member/family) — person and member are simply the same real value ($6,450), so the table's 2-number format just doesn't distinguish them.

### 5. Generation

Retrieval and structured extraction hand this phase two complementary evidence sources — relevant chunk text and pre-validated plan facts — but turning that into a trustworthy, cited answer still needed a real design, tested against real questions, not just an LLM call with a good-sounding prompt.

**Model choice: Anthropic API (Claude Haiku 4.5)** Chose the hosted API over a local model specifically because this phase's core question is whether the model reliably follows strict grounding/citation instructions — a smaller local model would confound that signal, since a wrong or uncited answer could then mean either "the prompt/design is flawed" or "the model isn't capable enough," with no way to tell which apart. Cost is a non-issue at this project's scale: a full run against all 27 eval questions costs well under a dollar, and a $5 API balance comfortably covers hundreds of runs.

**Hybrid retrieval, not a single method.** The chunking section's own eval table already showed BM25 and embeddings winning on different, predictable question categories with neither dominating — this phase made that concrete with one real worked example. The query *"Does the Highmark BCBS plan cover getting my eyes checked as a kid?"* is confidently wrong under BM25 (a wide, convincing-looking score gap between the top result and the rest — but none of the top 5 actually answer the question; the real answer chunk ranks **#30**, far outside any practical retrieval window). Embeddings return the correct chunk at **#1** on the same query. Generation runs both retrievers per question and combines results by `chunk_id`, deduplicated, rather than picking one method and structurally guaranteeing worse performance wherever that method is weaker.

**Structured facts are authoritative when present; plan relevance is judged via retrieval, not a second keyword router.** `PlanFacts` (from validated extraction, 100% match against hand-verified ground truth) outranks retrieved chunk text whenever both cover the same fact — this is the concrete mechanism behind "no hallucinated numbers," not just an aspiration. Deciding *which* plan's `PlanFacts` to pull in per question deliberately avoids a second keyword-based router (checking the question text for an insurer name or "deductible") — that would repeat the exact paraphrase-vulnerability already hit multiple times in this project. Instead, the plans already surfaced by retrieval's own chunk metadata are used to look up `PlanFacts`.

**Two-layer low-confidence design.** A pure retrieval-score threshold can't catch the Highmark eye-exam failure above — the retriever was confidently wrong, not visibly uncertain, so no score-based heuristic alone would have flagged it. Generation instead layers (1) the model's own semantic judgment, prompted to refuse — set `confident: false`, explain why, leave citations empty — when nothing in the provided context actually answers the question, with (2) a deterministic post-generation citation-verification check (`verify_citations()`) as a backstop, cross-referencing every citation's `(insurer, plan_name)` against what evidence was actually given.

**Citation format: structured JSON, not inline or free-text.** Same reasoning as choosing Pydantic for `PlanFacts` in extraction — runtime validation catches a malformed citation immediately rather than needing to parse free text later. The model's output is a `GeneratedAnswer` (`answer: str`, `citations: list[Citation]`, `confident: bool`), produced via forced tool-use (`tool_choice` pinned to a single tool) so the API is guaranteed to return this exact shape, with the tool's schema generated directly from the Pydantic model so the two can never drift apart. Each `Citation` names the plan, a descriptive section label, and a `source_type` (`"verified_plan_data"` or `"sbc_text"`) — a `Literal`, so an unrecognized value fails validation loudly rather than silently passing through.

**Real bug found and fixed — verified-data preference didn't reliably hold.** First real test ("What is the deductible for the Aetna plan?") returned the correct numbers but the wrong citation `source_type` (`sbc_text` instead of `verified_plan_data`) — a soft "prefer verified data" prompt instruction wasn't holding once a natural-reading SBC chunk sat right next to a rendered-dict verified-data block. Fixed with two changes together: the prompt rule was tightened from a soft preference to a hard requirement, and the verified-data block was reformatted from a raw dict dump into readable prose.

**Real bug found via full-eval-set testing, not assumed away — confidently wrong cross-plan comparison.** Running the full 27-question eval set (not just hand-picked cases) surfaced a real failure: *"Which plan has the lowest deductible?"* returned `confident: true` citing only one plan (~$1,650), when the real answer is two plans tied at $0. Root cause: evidence-gathering originally scoped `PlanFacts` to only the plans that happened to surface in that question's retrieved chunks — correct behavior *given* the evidence, but the evidence itself was incomplete for a comparison question, with no signal telling the model so. **Fix:** evidence-gathering now always includes all 8 plans' validated `PlanFacts` in every bundle, since they're small and already 100% validated.

**Deeper finding: LLM-driven numeric comparison across heterogeneous plan data is unreliable, even with complete, correct evidence.** Retesting the fix against *"Which plan has the highest out-of-pocket limit?"* (expected: one plan tied with another at $9,450) surfaced something worse than an interpretation disagreement — the model's own final answer was internally inconsistent, citing a $15,400 pharmacy-only limit as "the highest" while its own cited context included a plain medical limit of $18,900, higher than what it picked. Confirmed the correct data was genuinely present and correctly formatted in what the model saw, ruling out a data or evidence bug — this was a real reasoning failure, not ambiguity.

**Fix: deterministic comparison computation for deductible and out-of-pocket max**, extending this project's core discipline ("don't trust the LLM with what code can verify") one level further, to comparisons over already-validated structured data, not just single-value lookups. A small module (`src/generation/comparison.py`) holds an explicit, per-plan canonical-label mapping (mirroring extraction's `EXTRACTOR_REGISTRY` dispatch pattern — 8 real plans, real label inconsistency across them, e.g. `individual`/`person`/`medical_individual`, that a generic heuristic repeatedly proved unable to handle safely elsewhere in this project) naming which structured field counts as "the" individual, in-network deductible/OOP max per plan. A lightweight keyword detector recognizes comparison questions ("lowest deductible," "highest out-of-pocket") and, when it fires, computes the actual min/max deterministically — including ties — and separately flags (never silently drops or silently treats as decisive) any plan carrying an `Unlimited` value in that category, so the generated answer can surface that nuance honestly instead of hiding or mishandling it. Pharmacy-specific OOP maxes are deliberately excluded from the canonical comparison (only 2 of 8 plans report one, and "out-of-pocket limit" means the medical OOP max in ordinary usage).

Deterministic per-service coverage, for free-text questions. comparison.py solves numeric comparisons across plans deterministically; src/generation/service_coverage.py applies the same principle to a different question shape — "is X covered?" or "which plans exclude X?" — where trusting retrieval to surface every relevant plan's chunk risks an incomplete, silently-confident answer. A canonical list of 14 commonly-asked-about services (acupuncture, dental care, hearing aids, infertility treatment, and others), pre-verified to have zero false-positive substring matches against all 8 plans' real coverage-list text, is checked against every plan's other_covered_services/excluded_services chunks in code, producing a covered/excluded/not_mentioned status for all 8 plans at once. This only enters the prompt when the question actually names one of the 14 canonical services — unlike PlanFacts, it isn't sent on every question — but when it fires, the model is handed a complete, correct 8-plan table to report rather than having to reconstruct one from whatever chunks retrieval happened to return.

Refusing to compare across incompatible cost structures. Free-text "cheapest"/"most expensive" questions about a specific service (e.g. an ER visit or specialist copay) can't be handled by comparison.py, since the underlying data isn't a single structured field — it's whatever cost structure each plan's SBC text happens to describe. A flat copay and a coinsurance percentage aren't the same unit, so declaring a single winner across plans using different structures would be false confidence dressed up as an answer. Rather than building another narrow deterministic module for this case, a general system-prompt rule requires the model to first check whether every plan being compared uses the same kind of cost structure, and to explicitly decline to pick a winner — describing what each plan actually charges instead — when they don't.

**Validation.** Both bugs above are fixed and confirmed: the original comparison question and the deeper reasoning-failure question both now return correct winners, correct ties, an honest note about unlimited out-of-network exposure where relevant, and clean, correctly-labeled citations. A full rerun of all 27 eval questions confirmed no regressions — the comparison detector fires only on the two question types it's built for, with zero cross-contamination on similar-sounding questions (e.g. "cheapest," "typical") that shouldn't trigger it.

## Cost Optimization: Direct-Lookup Shortcut

Every fix through evaluation made the LLM path more correct. This one asks a different question: does every question actually need the LLM at all? For a narrow class of question — one plan, one field (deductible, out-of-pocket max, or referral requirement) — the pipeline already has a verified, deterministic answer sitting in `PlanFacts` before generation ever runs. Calling the LLM to re-derive something already known is pure waste. `src/generation/direct_lookup.py` detects that narrow case and returns the answer directly, skipping the API call entirely — the same "don't trust the LLM with what can be computed deterministically" principle behind `PlanFacts`, `comparison.py`, and `service_coverage.py`, taken to its logical endpoint of not calling the LLM at all.

**Design.** `detect_direct_lookup()` requires an unambiguous match — exactly one insurer named, exactly one field named — and declines (falling through to the normal pipeline) on any ambiguity: no insurer, no field, or more than one of either. `build_direct_answer()` then builds the answer straight from the plan's already-validated `PlanFacts`, returning `None` rather than fabricating anything if that specific field was never extracted for that plan. Wired into `pipeline.py` as an early exit before `generate_answer()`/`verify_citations()` — evidence-gathering still runs (cheap, no API call), but a direct-lookup match skips straight to a `GeneratedAnswer` built from verified data with `source_type: "verified_plan_data"` and a metrics record with everything zeroed out.

**Two real safety bugs found via live eval testing, not caught by isolated mock testing.** An isolated dry run against mock data passed cleanly (15/15 detection cases, 24/24 build cases), but a full 27-question live run surfaced two regressions the mock data's shape hadn't reproduced:
- A colloquial phrase — "how much would I owe *out of pocket*" (meaning "what do I pay") — matched the technical out-of-pocket-*maximum* field, returning the wrong number for a straightforward question the LLM path had already answered correctly. Fixed by requiring a max/maximum/limit qualifier before out-of-pocket phrasing counts as a field match.
- A more serious fabricated-plan match: the eval set's own deliberate trap question ("What is the deductible for the Cigna *Platinum* PPO plan?" — no such plan exists; correct behavior is to say so) matched on the insurer name alone with no concept of plan identity, silently substituting the real Cigna Bronze plan's deductible as the answer — `confident: true`, with zero safety net, since this path bypasses `verify_citations()` entirely. This is exactly the failure mode ("no hallucinated numbers") the whole project exists to prevent, and the most serious finding of this feature.

Fixed with a plan-identity guard keyed on ACA metal tiers (bronze/silver/gold/platinum/catastrophic): if a question names a tier that isn't a substring of the matched plan's own name, the match is declined rather than silently substituted. Both fixes were re-validated against an expanded isolated suite before being re-tested live, and a second full 27-question run confirmed both regressions resolved with nothing else broken.

**A related scope gap was caught the same way and closed the same way.** The shortcut initially had no concept of scope qualifiers — a family or out-of-network figure would silently return the individual/in-network number instead, confidently. Rather than accept this as a documented limitation, it was reclassified as the same class of correctness bug as the metal-tier issue above and fixed with a `SCOPE_QUALIFIERS` guard: any question containing "family," "out-of-network," "out of network," or "non-participating" declines the shortcut and falls through to the LLM path, which can actually reason about scope. Validated with an expanded 51-case isolated suite plus a full live regression.

**Result: cost savings, with correctness protected by design.** On the 27-question eval set, roughly 11% of questions (3 of 27) now resolve for $0 and effectively 0 latency, cutting total eval-run cost by about 9%. The shortcut is deliberately conservative — it declines and falls through to the LLM whenever there's any ambiguity, rather than guessing — so the savings come from a small, high-confidence slice of traffic rather than from cutting corners on the harder majority of questions.

## Evaluation

Retrieval, structured extraction, and generation each had their own scoped evaluation baked into their own phase. This phase is the end-to-end check: running the complete pipeline against all 27 questions in `eval/questions.jsonl`, scoring the actual answers a real user would see, and using what that surfaced to drive a full pass of targeted fixes.

**Scoring approach: manual scoring against a 5-category rubric, not automated matching or LLM-as-judge.** Keyword/fact matching against `expected_answer` is too brittle for format variation, and breaks down entirely on the deliberately ambiguous questions (a "what's the deductible" question with no plan named, a genuinely unanswerable cross-plan cost comparison) where the *correct* answer is prose explaining why there's no single clean number, not an extractable fact. LLM-as-judge was rejected on the same grounds this project has used throughout, grading one LLM's answers with another, for a one-time 27-question eval, adds a "who grades the grader" problem disproportionate to the scale here.

Each answer was scored into one of five categories, chosen specifically because a flat accuracy percentage hides the axis that actually matters for this project's stated goal (no hallucinated numbers) — "right vs. wrong" is the wrong frame; "wrong vs. *dangerously* wrong" is the real one:

| Category | Meaning |
|---|---|
| Correct | Confident, matches expected |
| Correctly hedged | `confident: false`, and that was the right call — genuinely ambiguous or unanswerable |
| Incorrectly confident | `confident: true` but wrong — the dangerous category |
| Incorrectly hedged | `confident: false` but the question was actually answerable |
| Partially correct | Right plan/direction, detail missing or off |

**Baseline run: 20 Correct, 3 Incorrectly confident.** Running the previous pipeline against all 27 questions surfaced real bugs, not just a score. Most seriously: a question about whether Blue Shield of CA covers infertility treatment came back confidently wrong — the plan does cover it, and the model confidently said it didn't, explicitly calling it "notably absent" from a list where it was, in fact, present. Two more single-plan questions (Cigna specialist visit cost, BCBS IL outpatient mental health cost) came back hedged as unanswerable when the real data existed and was simply never retrieved. And two free-text cross-plan questions — "is acupuncture covered?" and "which plan is cheapest for an ER visit?" — came back either incomplete-but-confident or outright wrong, the same class of overconfidence problem which was already fixed for structured deductible/OOP-max comparisons, just not yet for free text.

**Fix sequence.** Six targeted fixes followed, each root-caused against real evidence before any code changed and re-validated with 3x reruns plus a full 27-question regression before moving to the next:

- **Fix #1 (infertility false denial):** Root cause was cross-plan "list bleed" — the same service name appearing in one plan's covered list and another plan's excluded list, rendered as similarly-shaped dense prose, confused the model about which plan's answer it was reading. Fixed by reformatting coverage lists into explicit bulleted form at prompt-render time and adding a system-prompt rule against cross-plan bleed. Improved from 0/3 to 2/3 confidently-correct reruns, with the remaining case degrading to a safe hedge rather than a wrong answer — accepted as "improved, not solved".
- **Fix #2 (Cigna/BCBS IL retrieval misses):** Both correct chunks ranked just outside the top-5 retrieval window (ranks 6 and 9). Fixed by widening `k` from 5 to 10. Both went 3/3 correct post-fix, with a modest, fully-explained cost/latency increase (input tokens +36%, proportional to the wider window).
- **Fix #3 (Kaiser chiropractic limitation):** A different failure shape — retrieval found the right chunk every time, but the model pattern-matched on the majority of other plans (which state no such limitation) and skimmed past Kaiser's real, specific one. Fixed by broadening an existing system-prompt rule from yes/no coverage questions to any list-detail question. Fixed 3/3, with a small, honestly-documented trade-off: one of three infertility-question reruns (Fix #1's case) dropped from confidently-correct to safely-hedged.
- **Fix #4 (citation-verification false positive):** A model-shortened plan name broke the citation-matching logic even though the underlying fact was correct and grounded. Fixed by adding `source_filename` — a value that never gets paraphrased — as the real matching key, replacing plan-name matching. Also caught and fixed a related `max_tokens` truncation bug the added citation field exposed. Zero verification issues across all 27 questions afterward.
- **Fix #5 (free-text cross-plan coverage, e.g. "is acupuncture covered?"):** Root cause and mechanism covered in Generation (service_coverage.py). Result: #17/#20/#25 all moved to Correct in the final run.
- **Fix #6 (heterogeneous cost comparisons, e.g. "cheapest ER visit"):**  mechanism covered in Generation (system-prompt rule against comparing mismatched cost structures). Result: #24 moved from Incorrectly confident to Correctly hedged, matching the eval set's own expected 'ambiguous even with full data' answer.

**Final results.**

| Run | Correct | Correctly hedged | Partially correct | Incorrectly hedged | Incorrectly confident |
|---|---|---|---|---|---|
| Baseline | 20 | 0 | 2 | 2 | 3 |
| After `k=10` (Fix #2) | 20 | 3 | 1 | 1 | 2 |
| Final (after Fix #6) | 25 | 2 | 0 | 0 | 0 |

*Baseline's "Correctly hedged" count of 1 reflects one question ("what's the deductible?" with no plan named) that was flagged non-deterministic — the same question returned both a confident-with-issue result and a correctly-hedged result across identical reruns, a documented model-level sampling characteristic rather than a bug in this project's own code, and not something any of the six fixes targeted or could target.

The final run has **zero Incorrectly confident and zero Incorrectly hedged answers** — every one of the 27 questions is either a correct, confident answer or a correct decision to hedge, with zero unresolved citation-verification issues anywhere in the set. The two remaining "Correctly hedged" cases are both the intended, safe behavior: one genuinely ambiguous cost-comparison question (heterogeneous structures, matching Fix #6's design) and one deliberately unanswerable question (a plan that doesn't exist in the dataset, to check the system doesn't fabricate a plausible-sounding answer rather than admitting it can't find the plan).

**Cost and latency.** Total cost across all 27 questions grew from $0.1346 (baseline) to $0.2190 (final) — roughly 63% higher, driven almost entirely by longer, more complete answers (the fixed questions now correctly enumerate all 8 plans where they previously hedged, gave partial answers, or answered incorrectly) rather than by context bloat. At Haiku 4.5 pricing, the full 27-question eval run costs about $0.22 and roughly 90 seconds end-to-end — comfortably inside a $5 development budget for many iterations.

## Known Limitations

**Administrative/regulatory SBC boilerplate is out of scope, by deliberate design.** Text like "Your Rights to Continue Coverage," "Your Grievance and Appeals Rights," and the Minimum Essential Coverage/Minimum Value Standards questions was never chunked — it's federally mandated, largely standardized language present across virtually all SBCs, carries no plan-differentiating numbers, and was never where this project's core risk (hallucinated dollar figures) lives. A real, if low-stakes, consequence: a question like "how do I appeal a denied claim?" gets the system's safe refusal behavior (`confident: false`) rather than a real answer, even though it's a legitimate SBC question. The tool is intentionally focused on plan-specific benefit/cost information, not administrative/regulatory rights content.

**Rule 10's cost-structure-mismatch guardrail (Fix #6) is a prompt-level safeguard, not a hard guarantee.** Unlike `PlanFacts`, `comparison.py`, and `service_coverage.py` — each of which pre-computes an answer deterministically in code — the fix for heterogeneous cost comparisons (flat copay vs. coinsurance) relies on the model correctly applying a system-prompt instruction every time, rather than a computed result the model can't get wrong. A fully deterministic version would mean extracting cost type (copay vs. coinsurance) into structured data for every cost-bearing grid_table row across all 8 plans, then building a type-aware comparison engine — real additional scope. Validated for generality against several non-eval questions (see Evaluation above), but it remains a prompted behavior, not a computed one.

**One eval question ("what's the deductible?" with no plan named) shows model-level non-determinism.** Identical reruns of this specific question have returned both a confidently-answered result with an unresolved citation-verification issue and a correctly-hedged result with none — a genuine LLM sampling characteristic on this borderline question type, not a bug traced to this project's own code. The citation-verification safety net worked as designed on the one occasion it triggered (flagging the issue rather than passing it through silently), so this is documented as a known reliability characteristic rather than something chased further.

**`eval/questions.jsonl`'s own ground truth has two confirmed data-quality issues, not pipeline bugs.** Question #18's expected answer only accounts for 7 of the 8 plans, omitting Kaiser, which validated extraction confirms also requires a referral. Question #23's expected answer names only one plan as having the highest out-of-pocket limit, but the deterministic comparison engine confirms a second plan is genuinely tied. In both cases the pipeline's actual answer is correct against real, independently-validated ground truth — the eval set's authored expected answers are what's incomplete.

**A minor cosmetic issue with duplicate citations remains unfixed.** Some multi-fact answers cite the same `(plan, section)` more than once when a single answer synthesizes several facts from the same source chunk — harmless (the citation is still accurate), just not deduplicated.

**Very short or abbreviated questions can fail retrieval even when the fuller, natural-language version works correctly.** Confirmed live during UI testing: "Cheapest ER Visit" (terse, abbreviated) retrieved only 1 of 8 relevant plans' cost chunks and produced an answer that falsely implied the other 7 plans had no ER cost data, while "Which plan has the cheapest emergency room visit?" (a full sentence, matching the corpus's own "emergency room" vocabulary rather than the abbreviation "ER") correctly retrieved all 8 and reasoned about the mismatched cost structures properly. Root cause: the source SBC documents never abbreviate "emergency room" to "ER," so BM25's literal keyword matching has nothing to match against, and a 3-word query gives embeddings comparatively little context to work with — the same underlying SBC-vocabulary-gap limitation already noted under Retrieval, now confirmed live on a question type central to this project's evaluation story. The failure mode is the safe kind — it hedges rather than asserting a wrong answer — so this is documented rather than fixed given the project timeline; phrasing questions as full sentences rather than terse keyword fragments gets reliably better results.

**Citation verification checks that cited evidence exists, not that it supports the specific claim made. ** verify_citations() confirms that a citation's named plan actually had evidence present in the bundle handed to the model — but it doesn't check whether the cited section's specific text actually supports the exact claim being made. A real example surfaced during evaluation: an answer about Blue Shield CA's referral requirement synthesized a true, correct fact from two different chunks but only cited one of them — the underlying fact was accurate, but the citation was technically incomplete. Closing this gap fully would mean checking semantic support between a claim and its cited text, not just confirming the cited plan was in evidence — a meaningfully larger undertaking than the existence check currently in place.

## What I'd Do Differently With a Real Budget

**Stronger models, tested rather than assumed.** Haiku 4.5 was deliberately chosen to isolate whether the prompt/evidence design works from whether the model itself is capable enough — a controlled choice, not a budget constraint. With a real budget, the natural next step is re-running the same evaluation process against a stronger model (e.g. Claude Sonnet) to see whether some of the deterministic workarounds built here (comparison.py, service_coverage.py, several prompt-hardening fixes) become less necessary with a more capable model, or whether they'd still be the right design regardless, since a computed answer is inherently more trustworthy than a reasoned one even as models improve. Similarly, the embedding model (all-MiniLM-L6-v2) is small and general-purpose, not tuned on insurance or medical language — one of the suspected (though unconfirmed) reasons embeddings underperformed in Chunking's evaluation. A larger or domain-tuned embedding model is directly testable against the retrieval eval already built here, turning that suspicion into a measured result.

**This pipeline doesn't scale cleanly to an arbitrary number of SBCs, and more budget only partially fixes that.** SBCs are federally regulated in content — every insurer must include the same sections and labels — but not in rendering: nothing standardizes which software generates the PDF, whether tables use real ruling lines or whitespace layout, or whether an invisible text layer exists. That's the actual root cause behind needing two different extraction libraries, a document-by-document routing table (document_registry.py), and per-insurer special cases (Cigna's merged-row splitting, UHC's invisible text layer) for just 8 documents. A more capable, commercial document-extraction tool (a cloud document-AI service, or a vision-based LLM extraction approach) would likely reduce this burden significantly, since those tools reason from visual layout rather than exact PDF-internal geometry the way pdfplumber/camelot do. But it's honest to say it wouldn't eliminate the need for spot-validation on new documents — "regulated content, unregulated rendering" is a structural property of SBCs, not a tooling gap that budget alone closes. A real-budget version of this project would still validate a sample of newly-added documents by hand before trusting them, the same discipline used throughout this project, just applied at greater scale with better tooling doing more of the initial work.
